How to learn, run and get the most out of Kite Terminal

Kite Terminal is a semi-automated trading assistant. It scans your NSE watchlist after the close, puts every proposed trade in front of you for approval, sizes it against your risk limits, places the protective stop, trails it and reconciles with Zerodha. You decide what gets traded. This page gives you a training path, a daily routine, the doc to read for each job, what to verify, and how to use the app well.

Status, 5 November 2026: live execution is NO-GO, and LIVE new entries are disabled in the code. Use the terminal in DRY RUN, with KITE_TERMINAL_BROKER_WRITES=disabled. The frozen order path places the protective sell GTT for the full quantity as soon as Kite accepts an entry, before it fills, and a GTT acts on all of the account's holdings. Until a separately authorized fix (docs/PROPOSAL_EXECUTION_GTT_AFTER_FILL.md), every LIVE new entry is refused server-side (LIVE_ENTRIES_DISABLED) and LIVE cannot be armed. The real broker order path has also never been accepted by Zerodha. See Status.

Ticks on this page are saved only in this browser. The daily-routine ticks clear themselves each new day.

The mental model

How a trade moves through the app

The app automates all of these steps except one: the approval is yours. Once you know which part does what, you know where to look when something seems wrong.

Automatic · 16:00 IST

Sync data

The Autopilot downloads the day's daily candles for watchlist and holdings, checks freshness and expires stale signals.

Automatic

Strategy scan

Momentum Breakout and Trend Pullback look for entries. Exit and breakeven checks run on open positions.

Automatic

Risk engine

Runs six checks: R:R, capital per trade, stock and sector exposure, open positions, portfolio risk. Signals that fail go to "Blocked by risk".

You

Approvals

Open Signal Detail, read the evidence, then Approve and place, or Reject.

Automatic

Execution

Places a LIMIT or MARKET entry (or an AMO, with your consent). As soon as the broker accepts it, the app places the protective GTT, before any fill. In Dry Run both are paper (PAPER-O-…, PAPER-G-…). LIVE entries are disabled (see Status).

Automatic · every 20–180 s

Guard

The order monitor checks every 20 s, the trailing stop every 45 s and reconciliation every 3 min.

Automatic

Journal

A position closes only after the broker confirms the exit. Results land in the Journal, with Dry Run and Live kept separate.

Architecture

Components and boundaries

One local Python process on this PC serves the UI, the API and the background workers. Nothing in it listens beyond 127.0.0.1.

Launcher IMPLEMENTED

backend/server.py: binds 127.0.0.1:8000, one worker, no reload. Refuses a non-loopback bind unless remote access is explicitly allowed, and refuses a malformed KITE_REST_PROXY before anything else starts. Logs one Security summary: line ending in broker_writes=enabled|DISABLED.

API and UI IMPLEMENTED

backend/main.py (FastAPI) + backend/routes/; static UI in frontend/, served by the same process under a strict Content-Security-Policy. Every order-affecting check is server-side; the UI only displays it.

Database IMPLEMENTED

SQLite backend/kite_terminal.db with versioned migrations (backend/db.py). The Kite access token is stored only Fernet-encrypted (KITE_TERMINAL_ENCRYPTION_KEY in .env). Event tables are append-only.

Broker client factory IMPLEMENTED

backend/kite_client.py create_kite_connect() is the only place a KiteConnect REST client is built (test-enforced). It attaches the NET-1 proxy, ignores environment proxy settings, and narrows the client to read-only when broker writes are disabled.

Execution engine IMPLEMENTED · FROZEN

backend/execution.py places the entry and its protective GTT. Hash-pinned by the PK-25 manifest; not changed without separate authorization. Dry run runs the same code against backend/paper_broker.py.

Background workers IMPLEMENTED

Order monitor (20 s), trailing engine (45 s), reconciliation (3 min), Autopilot data jobs (16:00 IST). Health is tracked per worker; a dead or stale worker blocks live new entries.

Market-data ticker IMPLEMENTED

backend/ticker.py (KiteTicker WebSocket) connects directly to Kite, not through the proxy. Read-only price stream; it never places orders.

DMB Research Inbox IMPLEMENTED

backend/dmb_inbox.py + dmb_inbox_contract.py: file-based, user-initiated import of DMB bundles. No network link to DMB. Real bundles are refused until rights are approved.

Live Readiness IMPLEMENTED

backend/live_preflight.py + live_arming.py: read-only pre-flight; LIVE is armed for one Kite session only and a new login disarms it.

Localhost deployment and access model

  • Bind: 127.0.0.1 only. Exposing port 8000 to a network is not supported (DEPLOYMENT.md).
  • Host guard (TrustedHostGuard): only 127.0.0.1, localhost, ::1 on the served port; anything else is INVALID_HOST.
  • Origin guard (TerminalOriginGuard): API reads refused for cross-site or same-site (another port) fetches; writes need the X-Kite-Terminal header and a terminal Origin (CSRF).
  • Credential guard (TerminalCredentialGuard): every write, every non-public API read and the WebSocket need this launch's two-factor terminal credential, issued only by a completed Kite login.

Acceptance is not a fill

Kite's place_order returning an order id means only that the broker accepted the request. The ticket becomes executed with fill status pending, filled quantity 0 and no fill price. The frozen order path places the protective GTT right after acceptance, before any fill, for the full ticket quantity. Until the entry fills, that GTT protects nothing, and because a GTT acts on the account's holdings it could sell shares held outside this entry. The terminal therefore shows such a position as NOT_PROTECTED_PENDING_FILL, never PROTECTED, and LIVE entries are disabled until the fix is authorized. If the entry is later rejected or cancelled with nothing filled, the order monitor removes that GTT. A partial fill resizes it to the filled quantity, and every full fill verifies it at the broker. Partial fills are recorded as the broker reports them; a full fill only on COMPLETE. An exit order makes the position EXITING; the position closes only when the broker reports the full quantity filled.

BUY, SELL and exit controls are deliberately different

The P1-D review, the trading lock, the daily limits, the circuit breaker and critical reconciliation findings can only refuse adding risk. Linked exits, Quick-Action sells and Emergency Exit are never held back by them, so you are never stuck in a position. Exits still pass their own checks: the position must be open, owned by no other exit, and hold exactly the exit's quantity (one exit owner per position, enforced by a unique index).

Emergency Exit

  • Route: POST /api/kill-switch/emergency-exit-confirm. Needs a trading account, a current Kite session, the terminal credential and the CSRF header, plus the typed phrase EXIT ALL. After a restart or logout a fresh Kite login is required first.
  • Scope: LIVE open positions only, each in its own mode; a working entry is cancelled first. Best effort per position: one failure never stops the others, and a summary event is always written.
  • Same path: every exit runs through confirm_and_execute_ticket. With KITE_TERMINAL_BROKER_WRITES=disabled every sell is refused before any request (assurance 22b).
  • Never creates a GTT, including for a position whose own GTT failed. It sells only the broker-confirmed open quantity and refuses an unknown one (QUANTITY_UNKNOWN).
  • Not an entry: it is not held back by the LIVE-entry gate, LIVE not being armed, a stale P1-D review, the trading lock, the breaker, the interim guards or missing funds. A rejection is failed. A timeout or Kite session error is exit_outcome_unknown, sent once and never resubmitted.
  • No direct route: with KITE_REST_PROXY unset its SELLs are refused locally (a definite failure, nothing sent) with a message to exit in Kite web or the Kite app. Entries whose outcome is UNKNOWN are listed in not_exitable_unknown, never silently left out.
  • Status: IMPLEMENTED and tested with FakeKite (test_emergency_exit_safety.py); NOT VALIDATED against Zerodha. MARKET exits are not covered by Zerodha's sandbox.

The read-only broker switch

KITE_TERMINAL_BROKER_WRITES=disabled turns every REST client into a read-only one at the SDK's single request method. The only non-GET left is the login token exchange. Orders, GTTs, cancels, conversions and margin calculations are refused in this process before any request, whoever calls them (a route, a worker, Emergency Exit), and are recorded as definite rejections, never UNKNOWN. Any value other than enabled or empty disables writes. Start it as in Commands and check that the startup line ends in broker_writes=DISABLED.

Testing architecture

FakeKite, the wire recorder and the order-path assurance suite

Nothing in the automated suites reaches Zerodha. Tests use throwaway databases, never backend/kite_terminal.db.

FakeKite and synthetic tests do not prove real broker order acceptance or execution. They prove what this terminal does with each possible broker answer. What Zerodha actually answers, and whether it accepts this terminal's orders and GTTs, is untested. Real broker order acceptance remains unverified.

FakeKite

tests/fake_kite.py: an in-memory broker with an order book, GTT book, fills, and one-shot failures (raise_on_next: never reached the broker; accept_then_raise: accepted, response lost).

Wire recorder

tests/test_kite_rest_proxy.py: a real KiteConnect from the production factory, with requests' adapter replaced. Records method, host, path and the proxies the socket layer would use.

Demo server and browsers

tests/demo_server.py (scratch DB, FakeKite) drives e2e_ui.py, e2e_p1d.py, e2e_dmb_inbox.py and acceptance_dmb_kite.py in headless Edge.

Max advantage

How to get the most out of the app

The app helps you most by making each trade carefully, not by trading more often. These habits make the difference.

Never approve from the card alone

Signal Detail shows the exact candles the strategy used, each condition with its threshold, the six risk checks with real numbers, and how the size was calculated. One minute per signal there catches most bad trades.

A better watchlist gives better signals

The scans only see your watchlist and holdings. Keep it to liquid names you understand, and use Price-Volume Research to spot low traded value. The volume filters are what made both strategies profitable after costs.

Use the Smart Money score as context, not a ranking

Out-of-sample validation (PK-25) rated it LIMITED. Scores of 75 or more reduced expectancy in both test periods. Read the Volume context and Accumulation evidence to understand the bar, but don't filter or rank signals by the score.

Trust the revised defaults and don't over-tune

The September 2026 parameters were picked from the middle of ranges that worked in both halves of the data at costs up to 0.70%. A market-regime gate and a 52-week-high variant were tested and added nothing. Before changing a parameter, prove it with a net backtest and walk-forward.

Keep the Autopilot running

Keep the server running and logged in at 16:00 IST so the scan uses the day's final candle. If you miss it, starting the server or logging in catches up. Signals expire after a day, so review every evening.

Use all the safety controls

Use the trading lock, ₹ daily loss limit, max order value and 1 entry per day at first. They block only new entries, so you can be strict with them without risking getting stuck in a position.

Map every sector

An unmapped symbol skips the sector-exposure check without blocking anything. Clear the "unmapped symbols" helper every week so the risk engine can apply all six checks.

Act on exits and breakeven first

Exit signals and breakeven proposals protect profit you already have. Handle them before looking at new entries, every session.

Let the Journal decide

Check expectancy by strategy, not just the overall total. Ignore the numbers until there are at least 20 trades, and wait for 30 before going live. If a strategy is negative over a real sample, disable it, however good it looked in backtests.

Keep your data clean

Rebuild NEEDS_REFRESH symbols after splits and bonuses, since the live scan skips them. Back up weekly. The database holds your tickets, about 47k candles and the instrument cache, and git doesn't restore any of them.

Don't do these Run with --reload or more than one worker · expose port 8000 to a network (its access control is a per-launch browser credential for this PC, not a network login) · resubmit an order whose outcome is UNKNOWN · place a second order to "fix" a partial fill · trade the same symbols by hand in Kite while the app manages them · edit kite_terminal.db by hand · enable RSI Mean Reversion live · rank signals by the Smart Money score.
